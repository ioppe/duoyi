# AGENTS.md — 多仪 (Duoyi)

Cross-platform productivity app: **Flutter client** (Android / Linux desktop / macOS / Web) + **single-file FastAPI backend** (`backend/main.py`, ~12k lines, SQLite). Modules: Eisenhower todos, habit heatmap, pomodoro, calendar, profile. 8 switchable themes that change colors, background images, **and UI copy** (待办 → 咒文/委托/…) — user-visible strings come from `lib/core/brand_strings.dart`, don't hardcode them. `CLAUDE.md` holds the extended version of this guidance.

## Commands

```bash
flutter pub get
flutter analyze                     # must stay clean; CI pins Flutter 3.44.1
dart format .
flutter test                        # complete test suite under test/
flutter test test/screens/todo_screen_test.dart   # single file

# Backend (test_workspaces covers API routes; discover also includes auth/config/Web build policy)
cd backend && pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
python -m unittest discover -s . -v

# Release gate: Flutter tests + backend tests + analyze + debug APK build + device regression
scripts/alignment_regression_gate.sh
```

**Toolchains:** versions are pinned in `config/toolchain.json`. Executable locations use `FLUTTER_BIN`, `PYTHON_BIN`, Android SDK environment variables, or PATH; scripts do not assume a developer-specific installation directory.

## Hard rules (enforced by static guard tests)

About 100 files named `test/**/*_static_test.dart` regex-scan `lib/` and **fail the whole suite when banned patterns appear anywhere** — e.g. locally hardcoded font weights, raw values instead of design tokens (`lib/core/design_tokens.dart`), screens not using the i18n wrapper. When one trips: read the test's `reason` message (Chinese) and fix the code — never weaken the guard. Any UI change should be checked against them.

- **Typography**: all application UI uses the bundled `NotoSansSC` variable font (Noto Sans SC, offline) through `DesignTokens.fontFamily`. Body/secondary copy, input hints, menus and snackbars use `DesignTokens.fontWeightRegular` (400); buttons, navigation labels, chips and floating labels use `DesignTokens.fontWeightMedium` (500); titles, AppBar titles and emphasis use `DesignTokens.fontWeightStrong` (600). Shared typography tokens remain body 14 / secondary 12 / caption 11 / page title 18. Native Android uses `DesignTokens.androidFontSizeBody = 12` through the root `AppTypography` scaler (12/14), so its standard 100% body renders at 12 before additional system scaling and all other text roles keep their proportions. Native Android offers seven ratios 55/70/85/100/115/130/145%, with default 100% at the center and three steps on each side; Web (including Android browsers), iOS and desktop retain the shared baseline and original eight ratios 85–190%. Keep platform typography separate from saved application ratios and preserve nonlinear system scaling. Valid saved ratios remain intact; out-of-range values normalize to the nearest current-platform option without a forced default migration. Ordinary loading does not rewrite the stored ratio; previews retain the platform base and replace only the saved user ratio. Shared buttons keep `minimumSize: Size(0, DesignTokens.controlMinHeight)` with 16/10 padding so text scaling grows the control instead of clipping. Use theme text styles; do not hardcode `FontWeight` values or raw `fontFamily` strings, restore system serif/monospace families or add page-specific bottom-navigation typography. Font attribution and SIL OFL are in `assets/fonts/`; PDF export typography remains separate.
- **Web font loading**: `scripts/flutter_with_config.py build web` replaces only the generated Web FontManifest with a checked-in variable subset; the complete Noto font loads once after the first frame and idle delay. Native full-font registrations stay unchanged. Preserve this boundary; see `docs/web-font-loading.md`.
- **Subpage navigation**: use `AppPageTabs` / `AppPageSwitcher` (`lib/widgets/app_page_tabs.dart`) for content views within a screen. All themes share medium-weight labels, start alignment, horizontally scrollable labels and the short `PageTabIndicator`; avoid local pill/filled tab decorations. Date-range filters and form choices remain selection controls.

- **Version bump touches two files**: `pubspec.yaml` (`version: <name>+<build>`) AND `lib/core/app_version.dart` (`name`/`build`) — change together or update checks disagree. Read the actual values from those files rather than copying a historical example.
- **Backend routes are contract-pinned**: `backend/test_workspaces.py` asserts client-facing routes do not 404. Adding/renaming a route the client calls → add/update the matching contract test; keep `API_CONTRACT_VERSION` / `API_CONTRACT_FEATURES` in `backend/main.py` current.
- **Deployment config**: public defaults live in `config/deployment.json`; inject with `python3 scripts/flutter_with_config.py ...`. Installed login supports a persisted runtime URL + access token; `DUOYI_SERVER_URL` supplies only its initial URL. Web defaults to same-origin. Use `AuthProvider.client`/`baseUrl`; credentials and local data are bound to server + account. Private backend values come from environment or ignored `backend/.env`; see `docs/configuration.md`.
- **Configuration survives app updates**: device preferences live in platform user storage (`SharedPreferences` / `UserDefaults` / browser storage), separate from APK/`.app`/Web release files. Normal in-place updates must preserve saved preferences; keep application IDs, signing identity, sandbox/data-directory conventions and Web origin stable. Account cleanup still removes private account records and integration credentials, while retaining agreed device preferences. Saved values take precedence over new defaults; any migration must state its conditions and preserve user choices. See `docs/configuration-persistence.md`.
- **Approved application logo**: every client and the authentication header uses the user-approved **red rounded square (`#C85656`) with three white geometric blocks**. The master is `assets/logo/duoyi_app_logo.svg`, packaged source `assets/logo/duoyi_app_logo_1024.png`; keep the original `duoyi_logo_reference.png` as the approval record. Generate/check platform assets with `python3 scripts/sync_app_icons.py [--check]`. The old `duoyi_logo_redesign_1024.png` calendar and hourglass assets are historical, not the approved logo. Theme/version changes must not replace or recolor it. See `docs/branding.md`.
- **Browser favicon**: prefer the generated `web/favicon.svg` (`image/svg+xml`, `sizes="any"`) with transparent corners; keep a transparent PNG fallback. Do not reuse an opaque native-icon canvas for a browser tab or recolor the fixed red/white mark for dark mode. Transparency exposes the browser's own tab background; browser chrome/PWA theme colors are separate.
- **i18n**: Chinese ARB template (`lib/l10n/app_zh.arb`, zh primary / en); use `I18n.tr()` from `lib/core/i18n.dart`.
- **Time & locale**: user-visible dates/"today"/day stats/habit periods/reminders use the *application* wall clock — `AppClock` (`lib/core/app_clock.dart`) and `LocalTimezoneResolver` (`lib/core/local_timezone_resolver.dart`), default = system zone, user-overridable IANA zone. Keep sync timestamps, `updatedAt`, IDs, elapsed timers on real instants (`DateTime.now()`/UTC) and never shift floating date-only values. Language defaults to the system locale with a persisted explicit override (`LocaleProvider`, `language_settings_tile.dart`). See `docs/configuration.md`.
- **AI report archives**: completed statistical interpretations belong to account-private `ai_review_history`, grouped by natural week/month/year bounds plus captured IANA zone; store each input cutoff date separately. Use the application-level `AiService` for job state and durable history, never page-only result/busy state. Re-entry and period switching must restore the matching archive without resubmitting or showing another period's result. Guard late responses/writes across account cleanup. Waiting UI inherits the current Apple-style surfaces/tokens and uses truthful indeterminate/elapsed state, never a fabricated percent. See `docs/ai-report-history.md`.
- **Shared focus runtime**: signed-in clients on supporting backends use one server-authoritative runtime per account (`FocusSyncCoordinator` → `PomodoroProvider`). Send explicit versioned commands; snapshots never invoke local completion or resend controls. macOS panels and Android controls remain projections of that Provider. Preserve account/token generations, unique server settlement, device-local sound/permissions and concurrent ordinary login sessions. Visitors and confirmed unsupported backends keep local timers; transient failures must not create a second timer. See `docs/focus-runtime-sync.md`.

## Docs & deployment hygiene

- **Root documentation ownership**: the project root keeps only `README.md`, `DEPLOY.md`, `AGENTS.md`, `CLAUDE.md`, `LICENSE` and project/config entry files. The current canonical docs entry point is `docs/README.md`. One-off analysis and session handoff notes belong in the session scratch directory, never the repository. Verifiable evidence lives under `evidence/` with its historical hash manifests — those manifests are history records, keep them and never rewrite them to hide removed legacy file names. Build and last-run output is not committed (see `.gitignore`). Old root documents remain reachable through git history; do not copy them into an `archive/` directory.
- Backend service/container name and runner are configured in the deployment profile. For Docker code/image or Compose env_file changes, build the image and recreate the container; restart alone preserves the old image/environment. `scripts/deploy_backend_prod.sh` restarts and verifies the configured runner; `--check-config` only inspects values. Client releases ship through the configured Fork; bump both version files before a release tag.
- Sign-off repo secrets (`DUOYI_KEYSTORE_*`) are required for release builds — no debug-signing fallback.
- **Multi-platform installers on push**: every push to `main`, `self-hosted-skydrow`, `build/macos-dmg` or `fix/android-input-settings-device-test` must enter `.github/workflows/build-apk.yml`, pass shared configuration/analysis/tests, then build signed Android APKs, universal unsigned macOS DMG/ZIP and the Web desktop/mobile tarballs (`duoyi-web`) from the same commit and profile. Web tarballs stay upload-only on branch pushes except the `main` desktop tarball, which auto-deploys once the server entry and single Secret are configured; GitHub Pages remains `main`-only. Keep `build-macos.yml` reusable/manual-only to avoid a second automatic Mac run. Branch pushes upload artifacts; formal Releases remain tag-only. New pushes cancel unfinished runs on the same branch. Preserve signing gates and the trigger/dependency regression in `test/services/multi_platform_build_workflow_static_test.dart`.
- **macOS ad-hoc 发行签名与启动守卫**: the published macOS build stays team-less, so its outer `.app` must be re-signed with `macos/Runner/AdHocRelease.entitlements` (only sandbox, network client, user-selected files) and must NOT carry `keychain-access-groups`/`application-identifier`/`get-task-allow`; a passing `codesign --verify` is not proof the app launches (amfid Code=-424). Preserve the existing `Release.entitlements`, `DebugProfile.entitlements`, signing identity and bundle id; no development team is pinned in the repository, and developers who configure a team retain the Data Protection Keychain default. Only the ad-hoc CI build passes `--dart-define=DUOYI_MACOS_USE_DATA_PROTECTION_KEYCHAIN=false` (device-local AI config in the classic login keychain, never SharedPreferences/files). `scripts/macos_adhoc_package.py` owns prepare/verify/check-packages: verification must still reject a package whose codesign passes but whose signed entitlements are not exactly those 3 keys, and real ZIP/DMG checks must launch the app (pid, finishedLaunching, window, ≥3s liveness, exact-pid cleanup) plus the native classic-keychain write/read/delete round trip before upload. Never soften these guards with `continue-on-error`, skip-on-failure, hardcoded keychain options or by treating packaging success as launch success; the validation report is its own `duoyi-macos-validation` artifact. Developer ID signing and notarization remain unconfigured.
- **Self-hosted Web auto-deploy**: only pushes to `main` publish; the same-run `duoyi-web` desktop tarball goes through `deploy-self-hosted-web` → `scripts/deploy_web_ci.py` → the restricted root entry `duoyi-web-deploy` (profile `config/web-deploy.json`, key in the single repository Secret `DUOYI_WEB_DEPLOY_SSH_KEY`). Keep the release-directory + atomic `current` symlink layout, manifest verification and rollback; never delete old releases, execute payload files or touch backend/DB/Nginx. See `docs/web-auto-deploy.md`.
- **User-facing Release notes**: `docs/releases/<tag>.md` and GitHub Release descriptions explain application features, fixes, compatibility and installation. Keep GitHub Actions, CI, runners, build/test pipelines, packaging implementation, publishing gates and failed build history in developer documentation; do not present them as product features. When cleaning a published description, preserve its tag, version, assets and useful changelog links.

## Screenshots & evidence

- Store UI verification screenshots in `evidence/screenshots/`.
- Store larger screenshot batches in a named directory under `evidence/`.
- Do not leave generated agent screenshots in the repository root.
- Keep real app image assets in their existing asset directories, such as `assets/`, `android/app/src/main/res/`, `ios/Runner/Assets.xcassets/`, `linux/`, and `web/`.

- **Mainline integration**: follow `docs/mainline-integration.md`; before a client release, verify the candidate includes the intended local/origin branch heads, approved Logo reference/generator checks and the main-only self-hosted deployment job. A higher version number or green installer build alone does not prove these features survived branch integration. Never substitute historical calendar/hourglass artwork or deploy a tag artifact as a main push.
